# Local performance findings - 12 October 2026

The VOID release is pushed separately. This performance release includes its matching history-pagination migration, which is NOT applied to production. Apply it before deploying this version; the history API depends on the new function. Source instructions and current code were inspected first. Measurements use synthetic data; no live checkout or patient mutation was performed.

Confirmed in code: the patient picker rendered every matching patient, even an empty search with 10,000 patients; unchanged patient details triggered an extra sequential PATCH before checkout; receipt history loaded whole clinic tables and patient/file indexes with unpaginated reads; selected protected routes verified the same session in middleware and again in their route, adding two receptionist-session HTTP reads. Several existing history reads are capped by the database API, so a large unpaginated history could also be incomplete.

Changes: patient results display 100 rows with Show more and preserve full search; checkout sends only changed patient fields; receipt history pages 50 receipts/plan payments in one globally ordered result and fetches their linked details, retaining full plan-payment/visit rollups through pagination; selected self-authenticating routes skip duplicate middleware verification while retaining current session/clinic/role checks in the route. Anonymous HTTP probes returned 401. No permissions or session verification results are cached.

Synthetic 10,000-row benchmark (medians): patient-picker React server rendering 157.88 ms to 1.55 ms; generated HTML 4,767,611 to 48,011 bytes. The local filter itself took 0.40 ms, suggesting rendering mattered more than this filter in that test. Receipt-history database read 11.19 ms for the previous 1,000-row load versus 2.1 ms for 50 entries; payload 647,001 to 32,197 bytes. A controlled 25-ms network delay demonstrates that an unchanged patient saves zero extra PATCH requests; its timing includes test-harness overhead and is not a real checkout latency.

Actual local Next.js HTTP measurement using a localhost synthetic REST adapter: warm receipts HTML 76.7 ms, patient search 93.8 ms, history API 42.6 ms, VOID request saving 114.6 ms. Cold page response 3,167.3 ms includes development compilation. HTML timing excludes hydration and browser paint. Session/read/request paths are recorded in pos-performance-http-results.json. Search/history each made two session reads plus one data read; void saving made six backend requests. This is not production latency. Server-Timing headers were added to checkout/search/history for later live diagnosis without logging patient values.

Additional local fixes: the patient profile fetched receptionists twice and awaited four sequential stages (main data, latest visit, receipt items, then plan details). It now reads receptionists once and loads all dependent details together in the second stage. The bounded latest-visit lookup is retained because the larger receipt list can be capped by the data API. A generation check prevents older profile responses overwriting a newer patient's view or a closed modal. Loading clears and a message appears on thrown network failures.

The checkout page now starts its patient load alongside the seven setup reads. Duplicate overlapping patient reads share one promise within that page and the same session only; the promise is cleared on completion/failure. Fresh loads still issue a new request. Clinic/session changes discard stale results. This does not cache patient data or session verification globally.

Measured using the actual profile loader and a controlled 25-ms delay per query: median 124.51 ms before versus 65.66 ms after, with 13 versus 12 database reads (clinical notes are a separate request). This proves reduced waiting in the test, not deployed latency. Tests verify matching profile data, concurrent patient changes, failure/loading handling, empty-clinic behavior, duplicate clinic reads, fresh reloads, session isolation, and stale response protection. Reproduce with node scripts/patient-profile-performance-tests.mjs; results are in patient-profile-performance-results.json.

Still unconfirmed: deployed network distance, provider connection pooling, cold production starts, device-specific browser rendering, and whether saving in the live app has another delay. The previously supplied complete_pos_checkout average of about 119 ms measures database execution only and cannot identify end-to-end slowness. Live client profiling and a real production browser trace remain necessary to attribute the user's deployed delay. Full patient-list downloads and registration lookups remain optimization opportunities; replacing them with server search must preserve all supported search fields and registration duplicate checks. These additional fixes need no new database migration; the earlier receipt-history pagination still requires its separate migration.

Reproduction: node scripts/pos-performance-benchmark.mjs; node scripts/local-pos-http-benchmark.mjs (temporary localhost test server). Both create isolated synthetic data and explicitly apply the separate performance migration only in that local test engine. The JSON artifacts preserve the measured results. The performance API requires its matching database migration before being used against a database; neither the performance code nor migration was included in the VOID-only push.

Validation after the additional profile/startup changes: patient-profile-performance-tests passed all eight behavior checks; patient-search-security-tests passed; the existing synthetic picker/save/history benchmark passed; npx tsc --noEmit and npm run build passed. git diff --check passed. The pre-existing middleware-to-proxy deprecation warning remains. Release validation also passed the mixed history pagination/clinic-permission tests and targeted clinic-file tests (28 test scripts in total), anonymous HTTP probes on all six routes with middleware bypass, and the native multi-connection VOID approval/balance-collection race. History display now respects explicit clinic attribution when the receptionist belongs elsewhere. No production receipt or database schema was changed during this performance release.
